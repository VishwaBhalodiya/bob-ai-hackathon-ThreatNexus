# Solution Overview

ThreatNexus is an assessment pipeline with a dashboard on the front and IBM Bob at the back.
Everything that enters — a CEF line, a Suricata log, a SIEM JSON export, a STIX bundle — leaves
as a scored, correlated, MITRE-mapped alert with a verdict and a BLUF summary, and rolls up into a
Commander Brief.

## 1. Ingest multi-source feeds (`src/backend/services/feed_ingestor.py`)

| Format | Detected by | Parser handles |
|---|---|---|
| **CEF** | `CEF:` prefix | 7 pipe-delimited header fields (with `\|` escapes), `key=value` extension, syslog prefix timestamp, vendor → feed label |
| **syslog** | fallback | RFC 3164 header, Suricata/Snort fast-log (`[1:2024897:3] … [Priority: 1] {TCP} a.b.c.d:p -> e.f.g.h:p`), `key="value"` sensor lines |
| **JSON / NDJSON** | `{` or `[` | envelopes (`alerts`, `events`, `hits`…), one-level nesting (`source.ip`), 40+ field aliases, epoch / ISO timestamps |
| **CSV** | header row with known columns | sniffed delimiter, same alias resolution |
| **STIX 2.1** | `"type": "bundle"` / `indicator` | `ipv4-addr`, `domain-name`, `url`, `file:hashes` patterns; confidence + labels → reputation; `indicates` relationships → threat type |

Every event record is normalised to one canonical shape (`source_ip, destination_ip, event_type,
severity, timestamp, hostname, description, raw_log, source, feed_format`). Free-text event names
are resolved to canonical types by an alias table (`"ssh brute-force: 63 failed logins"` → Brute
Force). Records are **de-duplicated across feeds** (same actor + event + target within ±90 s) and
**linked to the asset inventory** by destination IP, then hostname.

STIX bundles do not create alerts — they update the IOC table and **re-score every alert that
references those indicators**, so new intelligence immediately changes the picture.

## 2. Correlate and separate genuine threats from false positives

Correlation runs at two scales (`correlation_engine.py`):

* **24-hour cluster** — how many other alerts share this actor or this asset → correlation score
  (feeds the risk formula).
* **±10-minute siblings** — the alerts that form this alert's immediate story → the timeline, and
  the input to **attack-chain detection**: a chain is flagged when the siblings span **≥3 MITRE
  tactics** *and* at least one of them is a genuine threat (so a cluster of suppressed noise is
  never promoted to an attack chain).

The verdict (`fp_classifier.py`) combines IOC reputation, corroboration, chain membership, asset
criticality, behavioural suspicion, feed severity and **analyst history** into a 0–100
genuineness score, then thresholds it:

| Verdict | Meaning |
|---|---|
| `GENUINE_THREAT` | act on it — appears in the brief's ranked list |
| `NEEDS_REVIEW` | mixed signals — appears in the brief, flagged for an analyst |
| `LIKELY_FALSE_POSITIVE` | suppressed from the ranked list, shown in the brief's *suppressed* section with the reason |

Every verdict carries up to five human-readable reasons ("Corroborated by 4 related alerts",
"Port Scan from an unknown source with no corroboration is typically benign noise", "Analysts
marked 2 previous alerts from this source as false positive"). Two guard-rails: a source with
≥85 reputation is never suppressed, and an analyst's own label on the alert always wins.

**Feedback loop.** `PATCH /api/alerts/{id}/feedback` re-assesses the alert immediately *and*
becomes a history signal (±20 points) for future alerts from the same actor / technique.

## 3. MITRE ATT&CK mapping (`mitre_mapper.py`)

One table maps every canonical event type to technique ID, name and tactic (T1110 Brute Force ·
Credential Access; T1486 Data Encrypted for Impact · Impact; …) and orders tactics in kill-chain
sequence. The same module resolves raw feed vocabulary, so `"Mimikatz-like LSASS access"` lands on
T1003 without anyone writing a rule. Coverage per tactic is exposed at `/api/mitre/coverage` and
rendered as a heat strip; chains are described as their tactic progression
(*Initial Access → Execution → Privilege Escalation → Credential Access → Command & Control*).

## 4. Prioritised BLUF summaries (`ai_engine.py`, `routes/brief.py`)

Every alert has a four-part BLUF — **bottom line** (one sentence: priority, verdict, action,
asset, reason), **situation**, **assessment**, **recommendation** — generated by **IBM Bob** from a
structured prompt containing the score breakdown, verdict signals and MITRE mapping. Bob is asked
for strict JSON; the response is validated and, on any failure or a 3-second timeout, a
deterministic template renders the same four fields so the UI never blocks.

`GET /api/brief` composes the **Commander Brief**:

1. **Posture** (CRITICAL / ELEVATED / GUARDED / NORMAL) and a single headline bottom line.
2. Situation · assessment · recommendation for the whole window.
3. **Active attack chains** with stage progression, targets and alert links.
4. **Ranked priorities** — genuine first, chain members first, then by risk; correlated
   duplicates (same actor, technique, target reported by several feeds) collapsed to one entry;
   likely false positives excluded.
5. **Suppressed noise** — what was filtered out and why, so command sees the whole picture.

## Design decisions

| Decision | Why |
|---|---|
| One `pipeline.assess()` for every path | The list view, detail page, analyze endpoint, rescore and brief can never disagree. |
| Verdicts and scores are *explained*, not just emitted | Analysts and commanders must be able to challenge the machine; every number has a breakdown, every verdict has reasons. |
| Suppressed alerts stay visible | "Separate false positives" must not mean "hide them". |
| Score on the strongest IOC anywhere in the log | A weak source IP delivering a link to a known phishing domain is a phishing alert, not noise. |
| Template fallback with identical shape | Bob makes the prose better; it is never a single point of failure for the demo. |
| Alias-based event normalisation | Feeds describe the same technique in dozens of ways; a resolver beats a rule per feed. |
